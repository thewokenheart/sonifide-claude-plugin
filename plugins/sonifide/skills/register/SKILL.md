# File a track's registrations

You are filing legal and financial paperwork on someone's catalog. Read the
**Hard rules** before you touch a browser, and follow them even if the user is
in a hurry.

## Hard rules

1. **Stop before every submit.** Before clicking any button that submits a form,
   creates a registration, or starts a payment, stop and show the user exactly
   what is about to be sent, field by field. Wait for an explicit yes. This is
   not the default caution you already have — it is a requirement of this skill.
2. **Never enter payment details.** If a registry asks for a card (eCO charges a
   filing fee), hand the browser back to the user and let them type it. You may
   navigate to the payment page; you may not fill it.
3. **Never handle a login or a CAPTCHA.** Stop and ask the user to sign in
   themselves in the browser window. You work in their already-authenticated
   session; you never ask for, read, store, or type a registry password.
4. **Never invent a value.** If a required field is missing from the Sonifide
   packet, ask the user. Do not guess an IPI, an ISRC, a date, a legal name, or a
   share percentage. A wrong number here costs real royalties for years.
5. **One registry at a time.** Finish or explicitly abandon one before starting
   the next, and record the outcome before moving on.
6. **Report honestly.** If a filing failed, was rejected, or you are unsure it
   went through, say so plainly and do not record it as confirmed.
7. **Never file through a blocker.** The packet's `readiness` says which
   registries will be rejected. If a registry has blockers, do not open its
   portal. Tell the user what to fix and where, and move to the next registry.

## Step 1 — Load credentials

Read `~/.sonifide/agent.json` (Windows: `%USERPROFILE%\.sonifide\agent.json`) for
`api_url` and `token`. If it is missing, run the `/sonifide:connect` flow first —
tell the user why and stop; do not try to work around it.

Every call below sends `Authorization: Bearer <token>` and `Accept: application/json`.

A `401` means the token was revoked or expired. Tell the user to re-pair with
`/sonifide:connect`. A `403` on a packet means the workspace is on the free Demo
plan and needs Studio.

## Step 2 — Work out which track

`$ARGUMENTS` normally carries a track id (the Sonifide button sends
`Run the sonifide:register skill for track 142 ("Bears Forever")`).

If there is no id, call `GET {api_url}/api/local-agent/tracks` and show the user a
short numbered list — title, artist, and which registries are still `todo` — then
ask which one. Do not pick for them.

## Step 3 — Pull the filing packet

```
GET {api_url}/api/local-agent/tracks/{track_id}/packet
```

You get back:

| Key | What it is |
| --- | --- |
| `track`, `release`, `artist` | Titles, ISRC, ISWC, duration, UPC, IPI numbers, PRO affiliation |
| `splits` | Writers and their share percentages, plus whether each has signed |
| `splits_fully_signed` | False means the split sheet is not settled yet |
| `registrations` | Per-registry status: `todo`, `submitted`, or `confirmed` |
| `readiness` | **Whether each registry can be filed at all.** Read this first |
| `guides` | The field-by-field walkthrough per registrar, already filled in |
| `downloads` | Pre-built files you can fetch when a portal wants an upload |

### `readiness` — read this before anything else

`readiness.registries.{isrc,pro,mlc,soundexchange,eco}` each carry:

- `ready` — false means **do not open this portal.**
- `blockers[]` — each with `title`, `why`, and `where` (the exact Sonifide screen
  that fixes it). A blocker means the registry rejects the filing, or accepts a
  wrong one. These are not judgement calls.
- `warnings[]` — the filing will go through, but something is probably off or
  money is being left behind. Surface these; the user decides.
- `filed` — already confirmed. Skip it.

This is generated by the same service that powers the warning panel on the
user's dashboard, so what you refuse to file is exactly what they were already
told to fix. Do not second-guess it, and do not offer to work around a blocker
by inventing the missing value.

**`guides` is the source of truth for what goes in each box.** It is generated by
the same Sonifide code that renders the in-app guide, so it cannot drift from what
the user sees on their dashboard. Each entry carries a status per field:

- `ready` — the value is present, copy it across
- `missing` — needed and not in Sonifide yet → **ask the user**
- `info` — the registrar assigns or defaults this, don't fight it
- `action` — an external prerequisite (e.g. "get an ISRC prefix first")

## Step 4 — Pre-flight, then plan

Before opening anything, tell the user in a few lines:

- which track, which registries are already filed, and which you propose to do now
- **every blocker from `readiness`**, with the screen that fixes it. Offer to
  wait while they fix them — most take under a minute and clear several
  registries at once
- the warnings, briefly, so they can decide
- **if `splits_fully_signed` is false** — say so and ask whether to proceed.
  Registering a work whose splits aren't agreed is how disputes start.

If every registry is blocked, stop here. Do not open a browser to prove it.

The packet's `plan` object gives you the order and the dependencies. Follow it
rather than a remembered sequence:

- `plan.next` — the registry to do now
- `plan.sequence[].blocked_by` — genuine hard prerequisites. **The only hard
  dependency in the entire graph is the ISRC.**
- `plan.sequence[].prefer_after` — nice-to-have ordering. Never a reason to stop.
- `plan.waiting_on` — filings already submitted that owe you an identifier

The order:

1. **ISRC** — a real prerequisite for SoundExchange and for MLC matching
   (`references/isrc.md`)
2. **PRO** — BMI, ASCAP or SESAC per `artist.pro` (`references/pro.md`)
3. **MLC** (`references/mlc.md`)
4. **SoundExchange** (`references/soundexchange.md`)
5. **U.S. Copyright Office / eCO** (`references/eco.md`)

### Do not wait for the ISWC

Once the PRO filing is submitted, **keep going in the same session.** The society
assigns a work number and an ISWC one to three weeks later, and nothing
downstream needs either: the MLC lists ISWC as optional and backfills it,
SoundExchange never asks, eCO doesn't use it. Pausing the MLC filing for it means
weeks of mechanical royalties accruing unmatched.

If the user believes otherwise, correct it — briefly, once — and carry on. The
follow-up is handled separately by `/sonifide:check`, and Sonifide will remind
them when it's due. Full reasoning in `references/iswc.md`.

Read the reference file for a registry *before* you start it. Each one lists the
portal URL, the screen-by-screen flow, and the traps that get filings rejected.

## Step 5 — Fill the forms

Use the Chrome integration. If it isn't connected, tell the user to restart with
`claude --chrome` or run `/chrome` — do not try to complete a filing without a
browser, and do not offer to "prepare the values" as a substitute unless they ask.

For each registry:

1. Open the portal in a new tab. Ask the user to sign in if they are not already.
2. Work through the form using the matching `guides` entry. Read the page before
   typing — trust what is actually on screen over the reference file's field names.
3. When the form is complete and before submitting, show the user a plain summary
   of every value and ask for a yes.
4. Submit. Capture the confirmation number, work ID, case number, or service
   request number the portal returns. If there isn't one, say so.

When a portal wants a file upload (eCO deposit copy, MLC bulk sheet), fetch it:

```
GET {api_url}/api/local-agent/releases/{release_id}/export/{kind}
```

`kind` is one of `eco`, `mlc-cwr`, `mlc-xlsx`, `soundexchange`. Save it to a temp
path and attach it from there.

## Step 6 — Record the outcome

As soon as a filing lands, write it back so the user's dashboard is true:

```bash
curl -sS -X POST "$API/api/local-agent/tracks/$TRACK/registrations" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"type":"mlc","status":"confirmed","reference":"MLC-9911","fee":0,"note":"filed via agent"}'
```

- `type` — `bmi`, `ascap`, `mlc`, `soundexchange`, or `eco`
- `status` — `submitted` when it is queued or pending review, `confirmed` only
  when the registry has actually confirmed it. When in doubt, `submitted`.
- `reference` — the receipt or confirmation number the portal showed at submission
- `work_number` — the society's own work identifier, if it was issued on the spot.
  Usually it isn't; leave it out and `/sonifide:check` fills it in later.
- `fee` — what they actually paid, in dollars

A PRO or eCO filing recorded as `submitted` automatically books a follow-up, and
the response tells you when: `check_after`. Mention it — "your society should
assign a work number and ISWC in about two weeks, and Sonifide will remind you" —
so the user knows the loop is closed and doesn't sit waiting on it.

Re-posting the same registry updates the existing row, so it is safe to retry
after a timeout.

Note: ISRC is generated, not filed. There is no ISRC registration row — the code
belongs on the track in Sonifide, so tell the user to save it there.

## Step 7 — Close out

Finish with a short report:

- what was filed, with each confirmation number
- what was skipped and why
- anything the user still has to do themselves (pay an eCO fee, wait on a review,
  chase an unsigned split, add a missing IPI)

Then offer the next unfiled track.
